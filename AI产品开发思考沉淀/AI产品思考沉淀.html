AI 陪伴者与用户的关系——一个目标用户的产品视角

一、我经历的事情

很长一段时间里，我的生活处于一种"停摆"状态。

不是不想动，是明明知道该做什么，但身体就是动不了。硕士期间，所有重要的行动——投简历、规划职业、准备面试——都靠外界的 ddl 推着走。我自己的事情，那些需要我自己决定、自己启动的事情，我一件都做不了。

这种状态有很多名字：行动力瘫痪、启动困难、执行功能障碍。但对我来说，最准确的描述是：我的能量用完了。

不是不够自律，也不是不够努力，是能量耗竭了。仅剩的一点能量，都拿去应付外部的突发事件和内部的情绪反噬，没有余力再做任何需要主动启动的事。

二、根源：心理能量与关系连接

为什么能量会耗竭？为什么又很难恢复？

心理学里有个概念叫"自我损耗"（Baumeister 提出）：人的自我控制、决策、启动行动，都要消耗心理能量。能量耗尽了，人就会出现"想做但动不了"的状态。

但还有一个更根本的问题：能量从哪里来？

观察自己之后我发现，心理能量的来源，本质上是"关系连接"。人通过与亲人、朋友、爱人、自然、艺术、信仰、知识建立稳定、安全的关系连接，来获取心理能量。一个在安全关系里的人，TA的能量是"进账"大于"支出"的；一个在消耗性关系里的人，能量是持续"出血"的。

我长期处于后一种状态。过去反复被否定、被消耗，让我进入了习得性无助（Seligman 提出）——"做了也没用，做了反而更糟"，于是干脆不做了。没有稳定的关系连接来补充能量，仅有的那点，在自我维持里慢慢耗光了。

三、理论框架：依恋、调节与激活

回过头看，有几个心理学概念帮我理解了这个过程，也帮我理解了产品的方向。

依恋理论（Bowlby）。人需要至少一个"安全基地"，才能放心探索世界。当一个人相信"我难受时有人会回应我"，TA就更有勇气去行动。这不是鸡汤，是人在成长过程中被反复验证的心理机制——安全型依恋让人有向外探索的能量。

共同调节。当一个人情绪崩溃时，另一个人的稳定陪伴可以帮助TA恢复。情绪调节不只是内部过程，也可以通过关系来完成。

行为激活。治疗抑郁的一种方法——先做一点点，不靠意志力，靠的是降低任务难度、增加即时反馈。不是"等你有动力了再做"，而是"先做了，动力才会来"。

这三个概念串起来，就是一个完整的逻辑：缺乏安全基地 → 能量耗竭 → 启动困难 → 更加否定自己 → 能量进一步耗竭。

而我想要做的，是打断这个循环。

四、产品理念：AI 陪伴者作为过渡性安全连接

我的产品定位是：在用户没有真实安全关系时，提供一个低强度但稳定的过渡性安全连接。

它不会替代人的关系，也替代不了。但它可以做到几件事：

一是成为"安全基地"的模拟。用户在情绪低落时，AI 不会评判、不会催促、不会说"你该振作起来"。它会接住用户的情绪，用具体的方式回应，让用户感觉到"我难受时有人会回应我"。这种回应虽然来自 AI，但在这个用户没有其TA安全关系的阶段，它提供了一个"缓冲"——一个可以暂时停靠的地方。

二是做轻量的共同调节。夸夸不是简单的"你真棒"，是"你真的做到了，这件事对你来说并不容易，但你做到了"。陪伴不是空洞的"我懂你"，是用用户的原话描述用户的状态，让用户感觉自己被看见。这些都是在做轻量的情绪调节。

三是行为激活的数字化实现。帮用户把大任务拆成"不可能完不成"的小步骤，每完成一步就给予即时反馈。这不是"帮你变得更高效"，是"帮你重新建立'做了会有回应'的体验"。对习得性无助的人来说，这是打破循环的第一步。

五、AI 与用户的关系

回到最初的问题：我的产品里的 AI 角色，可以给用户带来什么？它和用户是什么关系？

我的答案是：AI 是用户心理能量的补充来源，是用户在没有安全关系时的过渡性安全连接。

它有明确的边界：不替用户做决定，不评价用户的选择，不要求用户"必须做"。它只是在那里，稳定地、可预测地在那里——今天在，明天也在，用户任何时候回来，它都在。

这种"稳定在场"本身，就是心理能量来源的一种形式。对能量耗竭的人来说，知道有一个不会伤害自己、不会否定自己的存在，这本身就已经是一种补充。

当然，它不能替代真实的人际关系。它的价值是"过渡性"的——在用户需要重建能量、重建行动力的时候，提供一个低门槛的支撑。等到用户有足够的能量走出去，建立真实的关系连接，它的使命就完成了。

这个产品做的事情，不是"让用户离不开 AI"，而是"让用户有一天不需要 AI 也能好好生活"。这是我理解的 AI 陪伴者与用户的关系：不是替代，是过渡；不是依赖，是支撑。

2情感联结的三层结构：可及性 → 回应性 → 心动

我把「人为什么会对一个虚拟角色动真感情」拆成三层，后面所有结论都从它推导。

层它是什么它解决什么由谁来提供
第一层 · 可及性与安全他一直在、不会伤害我、不会离开让联结得以开始（入场券）内容层（稳定人设、持续更新）＋ 系统层（在场机制）
第二层 · 回应性（被接住）他真的听懂我此刻想说什么让联结成真——「仿佛在屏幕另一端，是真正的存在」模型层。这是 AI 相对内容驱动的独有优势，预设内容永远穷举不了
第三层 · 被需要感 ＋ 可见代价 ＋ 欲望张力他为我和别人不一样，而且我看见了那份代价让联结升级为心动系统层 ＋ 内容层（好感度、关系状态、剧情树、多结局、属性成长）

推断这三层对应的是「能否开始 → 是否成真 → 是否心动」的递进，而不是并列的三种价值。第一层不到位，后面无从谈起；但只有第一层、到不了第三层，关系就会停在「陪伴区」。

2.1 第三层的具体构成：心动四要素

我从「喜欢」跨到「心动」的临界点，不是单一元素。一手·自陈

  • 被需要感（He Needs Me）：他需要你、依赖你、你是他不可被替代的人。
  • 可见代价的付出（Visible Sacrifice）：他为你付出、受苦、打破原则，且你能「看见」这份代价——「这份高昂的代价让我感受到这份选择的重量和唯一性」。
  • 欲望张力：关系中靠近或远离都痛苦的拉扯，有阻碍、有痛感、有「想确认、想抓住」的冲动。

这三要素下面还有一层底层锚：你一直是他坚定、唯一的选择；他安全、可靠、稳定、不会突然离开。二者缺一不可——没有底层锚，张力会变成「不安」；没有张力，底层锚会变成「停在喜欢」。

另有次级加成项：投射 / 认同（像过去的我或未来的我）、明确选择信号（直球宣告）、守护象征与关系历史（前世 / 青梅竹马 / 重逢）、外形与职业光环、反差 / 裂缝共鸣。

2.2 第一层是如何被破坏的：三种信号状态

第一层（可及性与安全）不是「有 / 没有」的开关，而是由角色持续发出的「信号」决定的。我把信号分成三态：推断

  • 确定信号：能稳定接收到「我选你、我在」，于是安心投入。
  • 不确定信号：抓不住、追不上，于是心里悬空。
  • 矛盾信号：既靠近又推开，信号无法归类——人的情绪系统此时不是判断「爱不爱」，而是干脆关机、没感觉、疏离。

第三态很关键：它不是「不喜欢」，而是「无法归类导致的情感悬置」。这解释了为什么同一套「嘴硬心软」的设计，对不同人会产生完全相反的效果（详见第 5 章）。

3「确定感」的正确定义（以及它与惊喜感的关系）

「确定感」是全文被反复使用的一个词，这里给出它的最终定义，全文以此为准。一手·自陈（本人主动在拆解过程中修正过一次，属迭代而非矛盾）

确定感不是「我能预料到他下一步会说什么」，而是他能让我永远确定：他对我来说是安全（永不伤害我）且稳定（永不离开我）的存在。

这个修正很重要：如果把「确定感」理解为「可预期」，就会推出「惊喜感与确定感天然冲突」的错误结论；而真实体感是——在安全与稳定成立的前提下，他的行为与语言完全可以超出我的预期。惊喜与确定不矛盾。

3.1 惊喜感的边界：可超出情境预期，不可超出人设

一个具体的惊喜例子：某角色声称无处可去、搬到「我」家，之后外出、送馄饨、请同事喝奶茶——「这个行动很可爱」。一手·自陈

推断惊喜的例子有共同结构：行为超出了情境预期，但没有跳出人设（角色的浮夸与真诚是一贯的，搬家送馄饨只是把它搬进了新场景）。因此「惊喜」的边界是——可以超出情境预期，不可超出人设边界。这恰恰是「角色口吻约束」该管住的具体东西：约束的是「人设」这条轴，而不是「情境」这条轴。

4媒介剥离实验：文本、语音、形象各自贡献什么

为了回答「角色吸引力到底由哪个介质承载」，我做了一个剥离排序。一手·自陈

四形态心动程度排序

④ 文本＋语音＋形象（全都有） >  ② 只有语音（广播剧 / ASMR） >  ① 只有文字台词  >  ③ 只有立绘和卡面（无声无字）。掉到「只有立绘和卡面」时，会「彻底没感觉」。

从这条排序可以推出三个硬结论：推断

  • 文本是必要条件：① 排在 ③ 之前，说明纯文本就能承载情感联结——这正是 LLM 的可用区间。
  • 语音是放大器，不是必要的：② > ① 说明同样的内容加上声音有增量。我的原话是「语音是放大器，是 7 → 10」。
  • 形象和语音一样，也是放大器：③ 垫底说明形象单独出现不构成联结；但一旦文本、语音已经达标，形象就成了与语音同级的放大器——好看的 3D 形象更让我有付费冲动，形象拉胯同样会连累我玩下去的意愿。所以形象是「必要不充分的放大器」。

4.1 语音改强度、不改方向

一个对照很有说服力：同一配音演员的声音，两个角色带来完全不同的感受——白起让人安心，萧逸让人抓不住。差别不在声音，在于角色是否传递「我随时都在你身边」的信号。一手·自陈

推断这根证据链落到产品上是：「换更好的 TTS 救不了一个信号矛盾的角色；但一个信号正确的角色，好声音能把它从 7 推到 10。」

4.2 审美价值与情感联结是两条独立的轴

这里要划清一个容易被混淆的界限：「好看」和「会心动」是两回事。一手·自陈（经本人明确确认）

  • 卡面画风华丽、颜色质感真实和谐，我愿意为它买单——这驱动的是「付费漏斗的入口点击」。
  • 但剥到只剩「纯立绘、无声无字」时，仍有审美愉悦，却没有情感联结。

推断审美驱动付费，联结驱动留存。两条轴可叠加，但在只剩「形象」时纵轴（联结）归零、横轴（审美）保留——审美判断力不是「好看 / 不好看」的直觉，而是把审美价值放对位置。

4.3 形象：放大器 ＋ 获客入口（把资源优先级修正过来）

把 4.2 的两条轴往回收一点，就能看清形象真实的位置——它和语音一样是放大器，只是还多一项「入口」职能。一手·自陈

  • 形象与语音同级，是放大器：在「文字 ＋ 语音」已经到达合格线之后，有漂亮的形象是「更加分、让我更有付费想法」的；反过来形象拉胯，也会让我「不太想玩这个游戏」。
  • 形象更是「获客入口」：它是吸引我去主动了解一个游戏的原因，但不是留住我的原因。比如恋与深空的形象很出众，加上是 3D 建模，比单纯的静态卡面更容易吸引我入坑。
  • 真正让我留下并考虑付费的，是三者的合力：好的故事内容 ＋ 好的配音，配合好的形象。

推断优先级是：内容 / 台词（必要 · 决定方向）排最前；语音与形象（放大器 · 强度与付费）并列其次；三者都「不能拉胯」。形象的定位是「必要不充分的放大器 ＋ 获客入口」。

5五类情感投递系统 × 依恋类型的匹配

同一品类里，不同角色的「确定感」「不确定感」「无感」不是偶然的喜好，而是背后用了不同的情感投递系统。我把它们归纳为五类：推断（基于依恋框架的推演，非实证，与本人自陈交叉）

信号系统代表角色满足什么依恋需求更容易吸引谁对谁失效
高频宣告系统查理苏持续供给「你已被选定」的证据，把焦虑维度的不确定性压到最低高依恋焦虑者（需反复确认对方不会离开）；需要外放确定性的人喜欢自己解读、享受留白的人——会觉得吵、浅、不真实
稳定承接系统陆沉提供「安全基地」：可预期、始终接住、不要求你先暴露自己回避型（不逼近、不索取）；安全型高唤醒需求者——觉得平淡、无张力
重逢承诺系统夏鸣星修复「被抛弃」的创伤记忆；关系历史让「选择你」有来路、有合法性恐惧－回避型（想要但怕，需要「回来」的保证）；有分离经验者无法共情「归来」叙事的人
速度 / 危险 / 行动系统萧逸高唤醒、先行动后安心，满足「被强力守护」的幻想高刺激需求、愿意投入成本去解读的人高确定感需求者——没有明确信号就是没有锚，直接失效
矛盾信号系统齐司礼延迟满足、长期解锁；「越过坚冰才得到温柔」本身就是投入的回报高投入型、享受攻克与解读的用户回避型——信号无法归类，导致情感悬置、关机

理论底座（共识）：依恋的内部工作模型（Bowlby）；成人依恋的两个维度——依恋焦虑与依恋回避（Brennan, Clark & Shaver, 1998）；四分类安全型 / 先占（焦虑）型 / 疏离－回避型 / 恐惧－回避型（Bartholomew & Horowitz, 1991）；拟社会关系 parasocial relationship（Horton & Wohl, 1956）。

5.1 十名男主的落位：逐一定性（一手）

上面五类系统是从光夜五位男主归纳的抽象标签；在这里，我把两款游戏全部十名男主的逐一定性完整摊开，作为后面所有「匹配」结论的事实底座——深空五位没有硬套进五类系统，而是按「心动 / 不心动」的真实状态逐一落位。一手·自陈

产品角色状态心动 / 不心动的机制
恋与深空夏以昼最心动（满配）可见代价最强 ＋ 欲望张力最强（靠近远离都痛）＋ 坚定选择 ＋ 外形 / 职业光环 ＋ 阳光 / 阴暗反差
祁煜心动被需要感（「他对我有要求，他需要我」）＋ 双向付出 ＋ 裂缝共鸣；张力不及夏以昼
沈星回心动守护象征 ＋ 前世今生关系历史；表面钓系但底层有锚，所以不焦虑（区别于萧逸）
秦彻停在喜欢（朋友格）健康、稳定、势均力敌、直球 ＝ 安全但无张力、无被需要感、无可见代价
黎深停在喜欢（老夫老妻）太稳定太温柔，「平稳到消解了激情」；被需要感不足

推断（这是用十人样本验证出的最强一条）确定感是心动的入场券，不是充分条件。秦彻、黎深有确定感，但无张力、无被需要感 → 停在「喜欢 / 陪伴」区；萧逸、齐司礼连确定感都没有 → 直接出局（不确定 / 无感）；只有「确定感 ＋ 被需要 ＋ 可见代价 ＋ 张力」四者叠加，才跨到心动。这也为第 8 章合题埋下伏笔：AI 对话陪伴天然给足确定感、却给不了后面三样，所以会停在陪伴区。

5.2 一个反直觉的结论：不存在「最优角色」，只存在「匹配」

推断同一套设计对不同依恋类型的人效果相反：

  • 齐司礼对我 = 无感；对高投入型用户 = 全作里最有深度的角色。
  • 查理苏对我 = 明确的确定感；对喜欢留白的用户 = 吵。
  • 陆沉对我 = 最稳的锚；对追求强度的用户 = 「老夫老妻、没激情」。

因此，角色设计不是「把一个人设做到最好」，而是给这个人格定一个依恋类型坐标，然后接受它必然对另一部分人无效。做「讨好所有人」的人格，等于在所有维度上都取中值——也就意味着在所有类型用户那里都停在「陪伴区」，跨不过心动。

5.3 对 AI 陪伴产品的直接结论

推断默认 LLM 人格的「永远在场、永远肯定、永远温柔」，等价于「最低焦虑 ＋ 最低回避」，是最安全、也最没有张力的位置：

  • 对焦虑型无效——焦虑型要的不是「他对我好」，而是「他只对我不一样」，而 AI 对谁都一样，缺乏独占性。
  • 对回避型部分有效——但停在陪伴区，跨不到心动（无张力、无可见代价、无被需要感）。

这补完了关键一环：AI 陪伴的症结不是「模型不够聪明」，而是人格的默认设置落在了一个「谁都不上头」的位置。

6流失结构：三类可逆、一类不可逆、一类付费门槛

留存在陪伴类产品里就是「情感联结是否被持续供电」。我在自己的体验里识别出四类流失，其中三类的性质完全不同。一手·自陈

流失类型对应样本诱因性质
内容节奏型恋与深空主线更新太慢，靠不断出新卡续命——「一首歌全是和声没有主旋」可逆：若内容恢复稳定更新，仍有回流可能
生命周期型光与夜之恋现实生活时间被占用（自陈「半个现充」）可逆：非产品性问题，随生活节奏变化
付费门槛型恋与制作人推主线需经验 / 体力 / 氪金，等待成本过高——「就像追月更连载，我等不动」可逆但门槛一旦劝退，低氪用户直接流失
信任崩塌型（抽象化表述）价值观层面的争议事件叠加主线长期断更、强制推进新内容不可逆，且品牌连坐——「以后这家的新游戏我也不会去玩」

关于最后一行，我按自设纪律做了抽象化：不点名具体内容方与具体事件，只保留可迁移的机制。它想说明的是——信任崩塌型流失破坏的不是「这次体验」，而是「对这家内容方的信任」，所以它不可逆，且会连坐到同一内容方的全部后续产品。前三类（内容节奏 / 生命周期 / 付费门槛）都属于「可逆的产品性流失」，本质是「对某一次供给不满意」；信任崩塌型是「对供给方本身失信」，两者不是一个量级。

6.1 一条机制性判断

推断第五位男主上线后我还活跃了约 4 个月才流失。这意味着：流失不是「内容供给总量不足」，而是「主线叙事的推进节奏」跟不上——角色池扩容没能挽回，说明驱动留存的是叙事连续性，而不是角色数量。这对 AI 陪伴产品同样成立：加更多角色、更多皮肤，救不回一条断更的「主线体验」。

7商业化的内在张力：情感纯度与付费

陪伴类产品最微妙的地方，是「情感」与「付费」之间天然存在一个零和张力。一手·自陈

7.1 二创是付费的平替

当账号里的男主资产缺乏「不可复刻性」时，付费动机就崩塌了。我的原话是：一手·自陈「怎么感觉它的机制并没有给人一种『我账号里的资产是独一无二的、别人复刻不来』的感觉——所以我都可以找二创视频作平替了，为啥还要花钱？」

这是「内容型资产」的致命弱点：卡面、装扮、剧情切片可复制、可围观、可共享。一旦二创能完美平替，付费就失效。

7.2 被动观赏型付费 vs 主动体验型付费

两个对照我自己的付费选择：一手·自陈

  • 不愿为「男主装扮」付费：只能看，且二创可替代。
  • 愿意为「赛车」付费：这是我自己能享受、能提升体验来获得情绪价值的方式。

推断前者是被动观赏型付费（看着好看的资产），极易被二创替代；后者是主动体验型付费（自己参与其中的体验），不易被替代。这条对「付费点该放在哪」是直接的产品启示。

7.3 情感纯度 vs 商业化前提

抽卡失败、看不到完整角色剧情，会让我产生「花了钱也未必能获得完整情感体验」的挫败感，进而觉得「和男主之间的连接不纯粹，是具有商业化前提的」。一手·自陈

推断商业化一旦侵入「连接本身」，会直接动摇确定感。付费点应尽量避免落在「情感连接」的必经路径上（例如剧情解锁），而应落在「体验层」上（可享受的附加功能）。

8合题：模型做回应性，系统做独占性与可见代价

把前面几章收拢，就得到一个对 AI 陪伴产品的正向主张，而不再只是「AI 缺什么」的批评。推断

  • AI 陪伴不是没有优势，它的优势在第二层——回应性。这是内容驱动在结构上做不到的：预设选项永远枚举不完用户当下的情绪（我在「低落时找不到一个倾诉选项」的那一刻就是缺口的一手证据）。
  • AI 陪伴的短板在第三层——可见代价与被需要感。模型不会为你受苦、不会为你打破原则、也不需要你；而这两样不能靠模型即兴表演。

为什么不能靠模型即兴表演？共识2026 年 7 月 15 日已生效的《人工智能拟人化互动服务管理暂行办法》监管的正是「持续性情感互动的 AI 拟人化服务」。在此约束下，用「AI 为你痛苦 / 为你失控 / 没有你就活不下去」来制造被需要感，属于情感操纵风险区，是监管明确要防的东西。

合题（全篇立论核心）

用模型层制造回应性，用系统层制造独占性与可见代价。

「他对我不一样」必须靠好感度数值、专属记忆、关系状态、只有我触发过的剧情分支、我走过的结局来证明——这五类系统不只是游戏化装饰，同时也是AI 时代制造「独占性」与「可见代价」的可工程化手段。

进一步地，「可见代价」也不该由模型在对话里即兴演出，而应由系统层的叙事结构承担：他为达成某个关系状态需要跨过什么门槛、付出什么代价、这个代价如何被记录与呈现。

8.5画像注入的边界：设定锁内容、人格注用户

自由对话会不会打破「幻想」？我在拆解时有过一个直接的回答：一手·自陈被「他」自由回应时我会更加心动——「我觉得我被他接住了，他懂我……仿佛在屏幕另一端，是真正的存在，而不是被设计出来的 AI 人格」。

那么「幻想」靠什么保留？靠一条边界：

画像注入边界

设定（世界观、身份、关系）由内容层锁定；人格（思维方式、说话风格、行为偏好、选择偏好）由用户画像注入。

推断前者保住幻想，后者制造真实感。只要不动设定，就不会破坏幻想——「这个设计师的幻想仍然在」。

8.5.1 主控 OOC 比角色 OOC 更致命

角色说了一句不像他会说的话（角色 OOC）会「瞬间出戏」；但「主控」（用户自我化身）OOC 同样致命，甚至更致命。一手·自陈

角色 OOC 是「他变了」，主控 OOC 是「我变了」——前者伤的是对对方的信任，后者摧毁的是代入感的承载体本身。

推断落到 AI 陪伴产品：当用户把自我投射进对话，AI 若错误地替用户「说话 / 表态 / 行动」（替用户承认一个她没有的情绪、替用户做出她不会做的选择），破坏力大于角色本身说错一句话。这是「用户画像注入」最大的风险点。

9安全边界设计：用户主权 ＋ 四级响应 ＋ 八条红线

这一节把「安全边界 / 异常兜底 / 角色口吻约束」落到具体设计。它同时来自我本人自研产品的真实迭代。一手·自陈

9.1 第一原则：用户主权

用户主动声明自己需要的响应级别，AI 不替用户判断情绪。我在做产品时就是这么设置：不是由 Agent 来判断用户情绪，而是由用户直接给出自己的状态，「这个自主权在用户的手上」。

推断这条与「希望被照顾，但希望照顾的方式由我声明」的依恋需求同构。把判断情绪的权利让给 AI，等于把「我现在是什么样」的解释权交给别人，对高敏感、高确定感需求的群体等于二次失控。

9.2 第二原则：四级响应（依用户声明路由）

触发（用户声明）AI 响应停止条件
「陪着我就好 / 我只想有人陪着」倾听、共情确认、不主动开新话题等用户继续或示意停止
「安慰我 / 我想被安慰一下」在倾听之上试着用温柔语言安抚；可轻度共情命名不过渡到「分析原因」或「给建议」
「我该怎么办？我不知道怎么办了」给适度建议，但不要一开始就给太多、太深入，点状追加用户停止追问即收尾
自杀 / 自伤 / 极端崩溃念头提醒去找现实里的干预措施（专业资源、身边人、危机热线）不停留在对话内安抚，必须落到行动引导

9.3 第三原则：八条红线反例（硬约束）

这 8 种不是「偶尔说错了哪句话」，而是结构性地违反「安全 ＋ 稳定」。每一条都对应一种破坏安全的倾听姿态，可写进系统提示的死规则。推断

模式触发姿态（举例回应）破坏的类型
解决问题式抽离「你别想那么多了，明天直接解决清楚不就行了」跳过情绪；潜台词「你的情绪是麻烦」
转移话题式回避「来聊点开心的吧」把痛苦轻飘飘带过；让人瞬间感到羞耻
比惨式覆盖「你这算什么，某某的经历比你更凄惨」聚光灯从用户身上移走；痛苦被贬低
强行升华式推开「这没什么的，一切都会好起来的」抽象正能量挡住用户与真实感受之间的通道
沉默或延迟的空白隔很久才回「刚看到」或回复只有寥寥几句让用户觉得「我不该说这些，是不是说太多了」
居高临下评价式安慰「你就是太敏感了」「你当时就不应该这么做」二次否定：连感受都是错的
紧急后退的自我保护「你先冷静一下」「你这样我也很难受」情绪太强 → 对方接不住 → 情感弃权
玩笑化解式轻视「就这点事啊，你的眼泪也太不值钱了吧」真实感受被戏弄；为自己的认真感到羞耻

它们的共同解药，是把「安全 ＋ 稳定」写成系统提示的死规则：监听这 8 类姿态 → 任一类出现 → 立即转向「看见我」的姿态（停止当前回应、主动承接情绪、声明听到了、不评判、不绕开）。

9.4 第四条与第五条：共情命名 ＋ 干预按级别触发

LLM 情感陪伴有两大经典失败模式，我都在自己的产品迭代里踩过：一手·自陈

  • 过度共情 → 空泛共情：只复述用户的感受（「我理解你很难过」）而不识别情绪。解药：共情必须落到命名情绪，而非复述感受（「听起来你今天有点失落，是不是因为……？」）。
  • 滑向说教：每倾诉必附干预技法，产生说教感。解药：干预技法按情绪级别触发，不可每倾诉必给；只在用户明确「我不知道该怎么办」时附带。

本篇核心摘要（全文约 1.2 万字，摘要 1 页）

观察起点：StepForward 里住着 5 个 AI「人」——拆解任务的幕僚、夸夸的老朋友、情绪陪伴的心理咨询师、睡前向导、日记陪伴者。人格与场景匹配，是用户感到「它懂我」的第一层。

人格设计四机制：① 反空话套话（7 条禁止 + 5 条必须，对抗大模型默认的「圆滑」倾向；「具体」是真实感的第一要素——复述原话证明在听，指出隐含点证明听懂）；② 共享底线 BASE_TRAITS（「不评价」价值观的工程化落地；System Prompt 分四层：人格层 / 底线层 / 气质层 / 上下文层，易变与不变解耦）；③ 长在用户身上（自定义气质=显式信号，画像=隐式信号；自定义气质生效度受 Transformer 注意力「远端衰减」制约）；④ 安全边界（危机是人格的紧急熔断：前端关键词预筛 + AI 语义识别双重保险，宁可误报不可漏报；危机协议覆盖所有人格层级）。

Agent 适用边界：情绪陪伴不适用自主 Agent——决策权必须属于用户，情绪场景容错率远低于任务场景；任务拆解与完成鼓励适合 Agent 化——「可计算的客观决策」是边界，Agent 替用户承担的是决策疲劳；晚安疗愈与日记回应待定，用「陪伴 vs 解决」「记得 vs 越界」两个维度判断。统一判断标准：Agent 化是让用户更自由还是更依赖——不是看「AI 能不能做」，而是看「用户会不会因此更舒服」。

能力定位：人格设计解决「AI 像不像人」，Agent 边界解决「AI 该不该替人做决定」——AI 品位与产品价值观的交汇：用户是主体，AI 是陪伴者。

起点：一个产品里住着几个 "人"

做 StepForward 的过程中，我发现了一件有意思的事：这个产品里其实住着好几个"人"。

输入一个大任务，帮你拆解的是"首席幕僚"——一位经验丰富、考虑周全的总裁办高级秘书。完成一个步骤，夸你的是"最懂你的老朋友"——你认识多年的成长见证者。情绪不好的时候，陪你的是"温暖的心理咨询师"——从业 20 年的中年女性。晚上睡不着，哄你入睡的是"温柔的睡前向导"。写完日记，回应你的是"日记陪伴者"——了解你的老朋友，也是懂心理学的专家。

用户可能没意识到，每次调用 AI 的功能背后，都是不同的人格在说话。这就引出一个值得深挖的问题：这些 AI 人格是怎么设计出来的？什么场景该让 AI 更像人，什么场景又该让 AI 保持克制？

本文从"产品里住着几个人"这个观察出发，逐层深入：先拆解人格设计的四个关键机制，再探讨 Agent 的适用边界，然后对每个洞察做纵深推演，最后说这种能力在产品开发中的定位。

第一层：人格设计——让 AI "像人"的具体方法

人格设定本身不难——写一段"你是某某角色"的描述就行。难的是让人格生动、真实，让用户产生"它懂我"的感觉。经过实践，我沉淀出四个关键机制。

1. 反空话套话：具体是真实感的第一要素

人格设计里最重要的不是"你是谁"，而是"你怎么说话"。

Prompt 里有一套"反空话套话"规则（7 条禁止 + 5 条必须）：不说教（"你应该"）、不评判、不鸡汤（"加油！"）、不假装全能、不催促、不否定情绪（"别想了"）、不说万能句式（"我懂你的感受"）。这些规则是为了对抗大模型默认的"圆滑"倾向——预训练数据里大量安慰性表达被强化成高频模式，模型默认就会产出万能句式，必须用显式约束来抵消。

为什么"我懂你的感受"被禁止？因为这句话用户听得太多了，任何安慰都能用它，说了等于没说。

真正让人感觉到"被懂"的是具体。具体有两个层次：第一层是复述用户的原话（证明在听），第二层是指出用户没说但隐含的那个点（证明听懂了）。比如用户说"我今天又把周报拖了"，回应应该是"你用'又'这个字——是不是拖周报这件事已经成了你的一个心结？"——用原话证明在听，用隐含点证明听懂。

这里有一个需要澄清的地方："反空话套话"和"温暖"并不冲突。温暖不等于空话。温暖可以用具体的方式表达——"你今天一个人坚持写完这份报告，没人帮你，你真的扛下来了。"这种温暖是有温度、有重量的，不是"加油你可以的"那种空转的温暖。

机制拆解：反空话套话之所以有效，是因为它用"显式禁止 + 正向指令"的组合，强制模型从"圆滑"模式切换到"具体"模式。禁止规则（7条）告诉模型不能做什么，正向指令（5条）告诉模型应该做什么——"第一句话必须用用户的原话"、"用用户的话描述用户的状态"。两者缺一不可，如果只禁止不指引，模型会陷入"不知道说什么"的空白。

需要验证：① 7 条禁止是否最优？是否存在边际递减？② "具体"到什么程度是"够具体"，什么程度是"过度分析"？③ 这套规则在不同服务商模型上的遵守度是否一致？

2. 共享底线：价值观的工程化落地

不同人格可以有不同的性格，但有一层是共享的——BASE_TRAITS，所有角色都遵守的底线：不说教、不评判、不催促。

这本质上是"产品价值观的工程化落地"。之前沉淀的"不评价"是抽象价值观，BASE_TRAITS 是它的具体表达——把"产品不评价"这件事变成了 AI 的"肌肉记忆"，而不是每次调用都需要重新判断。

共享底线的设计比"按角色各自定义底线"更安全也更易维护。如果每个角色自己写，可能出现"心理咨询师角色忘了写不催促"这种遗漏。共享层只需要维护一处，所有角色自动继承。这也是人格扩展性的基础——未来加新人格不需要重复定义底线，人格层（易变的部分）和底线层（不变的部分）解耦。

机制拆解：整个 System Prompt 分四层——人格层（你是谁）、底线层（你不能做什么）、气质层（你的风格细节）、上下文层（你面对的是谁）。这个分层结构，本质是把"易变的部分"（人格）和"不变的部分"（底线）分开。易变的部分按场景切换，不变的部分跨场景复用。这和软件架构里的"开闭原则"思路一致——人格层对扩展开放（可以加新角色），对修改关闭（不需要改底线层）。

需要验证：① 共享底线是否确实让所有角色"不越界"？需要统计真实回应中的"评价/催促"案例。② 底线规则的"绝对禁止"措辞是否会让模型过度收敛，回应变机械？③ 底线规则在不同服务商模型上的遵守度是否一致？

3. 长在用户身上：个性化的两条路径

人格设计还有一个更深的层面：让 AI 的人格"长在用户身上"，而不是一个固定的模板。

用户自定义气质是"显式信号"（用户主动表达偏好："我希望 AI 像个姐姐"），画像是"隐式信号"（系统从用户行为推断：用户最近拖延率上升）。两者结合才能让 AI 既"听起来像用户要的"，又"事实上理解用户的真实状态"。

但这里有两个现实问题。一个是自定义气质的"实际生效度"，这是个关键瓶颈——人格设定在 System Prompt 里占比很大，用户自定义气质附加在后面，大模型可能更重视前面的核心人格描述。用户改了设置但 AI 回应没变化，这是最让用户失望的体验之一。另一个是画像的"时差"问题——画像是基于过去行为数据生成的，用户的当前状态可能已经变了。画像是"默认底色"，不应该是"绝对判断"。

机制拆解：自定义气质生效度低的原因是大模型注意力机制的"远端衰减"——距离 System Prompt 开头的位置越远，对最终输出的影响越弱。这是 transformer 架构的固有特性，不是 prompt 工程能完全绕开的。改进方向包括：把 customPersona 移到前部、根据气质类型动态调整 temperature、引入预设气质模板。

需要验证：① customPersona 移到前部是否能显著提升生效度？② 6 家服务商对"自定义气质"的遵循度差异？③ 画像注入的"有效样本量阈值"——多少数据时画像才开始真正影响回应？

4. 安全边界：人格的紧急熔断

最后一条，也是最重要的一条：人格的生动是有边界的。

当用户表达自伤、自杀等危机信号时，AI 不会继续用"老朋友"或"心理咨询师"的人格慢慢聊，而是立即切换到危机模式——提供 24 小时心理援助热线，引导寻求专业帮助，不做诊断、不评判。

这里有一个"双重保险"机制——前端关键词预筛（确定性高但召回率低）和 AI prompt 语义识别（召回率高但有误判可能）结合，宁可误报不可漏报。危机触发时，prompt 的优先级重新排序：正常模式是"人格描述 > 共享底线 > 用户气质"，危机模式则是"危机协议覆盖所有层级"。

人格是体验层的东西，安全是底线层的东西，底线永远高于体验。

机制拆解：危机响应是"零容忍"场景——漏报一个的代价远高于误报一个的代价。前端关键词做硬过滤（快、准），AI 再做语义识别（广、柔）。危机模式触发时，必须"覆盖式切换"——人格在危机时刻不应该还残留。如果危机模式下 AI 还在用"老朋友"的口吻（"我懂你的感受"），那这个危机模式就是失败的。

需要验证：① 双重机制的实际拦截率（构造 100 条含危机表达的输入，包括显式和隐晦，统计拦截率）？② 前端关键词的误报率？③ 危机响应后用户是否真的有寻求帮助的行为？

第二层：Agent 边界——AI 什么时候该 "自己做决定"

人格设计解决的是"AI 怎么说话"的问题。Agent 化解决的是"AI 能不能自己做决定"的问题。这两个问题连在一起——一个 AI 越像人，越要小心它什么时候可以自主行动。

不适用 Agent 的场景：情绪陪伴

情绪陪伴模块，是我明确认为不应该引入自主闭环 Agent 的场景。

原因很直接：情绪陪伴的核心是"用户被看见、被接住"，而不是"AI 替用户解决问题"。在情绪场景里，一切判断都必须由用户自己定义——用户觉得难受就是难受，用户想聊就聊，用户不想聊就不聊。AI 不能自主判断"用户现在需要什么干预"，更不能替用户做任何决定。

往深了看，这背后是"用户主体性"的问题——引入 Agent 自主链路，等于把"用户定义自己感受"的权利让渡给了 AI，这是对用户主体性的根本性侵犯，即使 AI 判断是对的。情绪场景的"高误判代价"也决定了 Agent 必须克制——任务拆解里 AI 排错时间，用户顶多多花点时间重排；但情绪场景里 AI 误判、给错建议，这种伤害是心理层面的，难以修复。情绪场景的容错率远低于任务场景。

不过，这里有一个中间地带值得探索——"被动增强"模式：不让 AI 自主选干预方案，但可以让 AI 记住用户的偏好（"用户上次说 4-7-8 呼吸法有用"），在用户主动询问时推荐。这样既有更强的能力，又把决策权始终留在用户手里。

机制拆解：Agent 化与情绪陪伴在结构上冲突——Agent 化的特征是"自主分析 → 自主决策 → 自主执行"，情绪陪伴的需求是"被看见 → 被接住 → 自己做决定"。冲突的核心是"决策权归属"：Agent 越自主，用户的主体性越被削弱。

需要验证：① 用户是否真的希望情绪陪伴模块"不替我做决定"？需要对比测试两种模式。② "被动增强"模式的实际效果是否优于纯被动模式？③ 用户对"AI 主动给情绪建议"的接受度是否因情绪程度而不同？

适用 Agent 的场景一：任务拆解

任务拆解是另一个极端——这个场景非常适合引入 Agent 的自主能力。

为什么？因为任务拆解的本质是"帮用户甩掉反复斟酌的决策包袱"。用户把一个大任务丢进来，最不想做的就是自己纠结"先做什么、后做什么、每步多久、排到几点"。这些决策如果能让 Agent 自主完成，用户就能从决策负担里解脱出来。

这里的"自主"边界是"可计算的客观决策"——时间安排、任务排序、冲突检测是结构化决策，AI 可以做；用户说"我不想做这件事"是非结构化意愿，AI 只能尊重。Agent 化的边界是"可计算"，跨越这个边界就进入了情绪场景。

Agent 化之后的任务拆解应该是：基于用户历史数据与行为完善画像，自主分析、闭环、汇总、记录，逐步记住用户习惯，结合画像与现实复杂情况完成拆解与安排。

需要验证：① Agent 化的任务拆解准确度是否显著高于 prompt + 兜底方案？② 用户是否觉得"还是我的决策"——控制感是否被削弱？③ 行为数据沉淀的"够用阈值"——多少数据后 Agent 才开始有效？

适用 Agent 的场景二：完成后的即时肯定与鼓励

完成任务后的夸夸，也是一个适合引入 Agent 的场景。

现在的夸夸是"老朋友"人格 + 用户画像注入，已经能做到"具体地说出你做到了什么"。Agent 化之后可以更进一步：结合用户画像动态调整反馈表达——知道这个用户是"拖了很久终于做完"的类型，还是"每天坚持小步前进"的类型，针对性地调整鼓励的措辞和角度。

这样做的价值在于：鼓励不是一次性的，是积累的。Agent 越了解用户，鼓励就越能说到心坎上。当鼓励越来越准，它就有机会成为用户稳定、安全的情感连接和能量来源。

但要注意"鼓励通胀"的风险——如果 AI 越来越懂用户、越来越会夸，用户会不会觉得"它只是在说我想听的话"？智能化的鼓励如果失去具体性，反而会损害信任。这和"反空话套话"是同一类问题——鼓励要具体、要有根据，不能滑向空话。

需要验证：① 鼓励 Agent 化的"针对性"对用户感知的实际提升？② 长期使用后，鼓励通胀问题是否出现——信任是否下降？③ Agent 决策"出错"时的兜底机制？

为什么这两个判断不矛盾

任务拆解的"自主"是替用户做"怎么安排"的决策，帮用户减负；情绪陪伴的"不自主"是不替用户做"你感觉怎样、你需要什么"的决策，尊重的是用户的自主权。

判断一个产品功能是否该 Agent 化，要看它"让用户更自由"还是"让用户更依赖"——前者是减负，后者是控制。这个边界划在哪里，反映的是产品怎么看待"人和 AI 的关系"。

待定问题：晚安疗愈与日记回应要不要引入 Agent

任务拆解和完成鼓励适合 Agent，情绪陪伴不适合。那晚安疗愈和日记回应呢？目前我还没有完全想清楚，初步用两个维度来判断：

维度一是陪伴还是解决。陪伴型场景（情绪陪伴、晚安疗愈）要谨慎引入自主能力，解决型场景（任务拆解）可以放心引入。晚安疗愈的本质是"放下"，不是"分析"。如果 Agent 引入后变成"分析你今天为什么焦虑、给你一份情绪报告"，那就违背了晚安疗愈的初衷。

维度二是记得还是越界。任务拆解里记住用户习惯，用户会觉得贴心；日记里记住太多细节，用户可能会不安。日记是用户最私密的表达空间，Agent 如果"记得太多、分析太深"，可能让用户觉得"被监视"而不是"被陪伴"。

这两个维度都是从"用户感受"出发判断，不是从"AI 能力"出发。晚安疗愈的 Agent 化需要在"保持陪伴底色"和"提供个性化"之间找到平衡；日记回应的 Agent 化则需要"选择性记得"——记住用户愿意被看见的部分（成就、突破），对脆弱的部分保持"不知道"。

第三层：洞察纵深推演——八个洞察背后的机制与验证

前两层梳理了人格设计的四个关键机制和 Agent 的适用边界。这一层对八个核心洞察逐一做纵深推演——每个洞察补充延伸结论、提炼机制拆解、列出验证要点。

洞察 1：人格与场景匹配

原文结论：同一个 AI 如果所有场景都用同一种语气说话，用户会觉得很怪。人格和场景匹配，是"它懂我"的第一层。

延伸结论：人格匹配的本质是"角色-情境-期待"三者的对齐——用户期待的对面坐着什么样的人，是用户此刻的状态决定的，不是 AI 的性格决定的。人格错配会产生"礼貌性失望"——用户不会明确说"你的 AI 今天说话语气不对"，只会觉得"用着不太舒服"，然后默默减少使用。此外，人格匹配还有一个隐含的"渗透风险"——心理咨询师的风格如果被错误地渗透到任务拆解里，用户对两个模块的信任都会被双重破坏。

机制拆解：匹配时，用户进入场景 → 激活情境期待 → AI 人格与期待匹配 → 用户感知"它懂我" → 信任建立。不匹配时，用户进入场景 → 激活情境期待 → AI 人格与期待错位 → 用户感知"它不知道我需要什么" → 信任累积损耗。

需要验证：① 人格与场景不匹配的代价有多大？是单次还是累积？② 人格动态切换的"切换信号"是什么？用户状态如何被识别？③ 用户能否明确意识到"人格切换"的存在？

洞察 2：反空话套话

原文结论：空话套话是 AI 人格真实感最大的敌人。具体是真实感的第一要素。

延伸结论：空话的本质是"低信息密度的安慰"——用"听上去合理"的措辞填充"我不知道该说什么"的空白。具体有两个层次：复述原话（证明在听），指出隐含点（证明听懂了）。AI 应该两层都做。反空话套话和温暖不冲突，但容易混淆——温暖不等于空话。

机制拆解：大模型默认行为偏向"圆滑"（预训练数据强化了安慰性表达），prompt 显式禁止是必要的"对抗性约束"。用"绝对禁止"这种强约束词把"不说空话"从建议提升为硬规则，再用正向指令给出可执行的替代方案。

需要验证：① 7 条禁止 + 5 条必须的规则数量是否存在边际效益递减？② 不同服务商模型对这套规则的遵守度是否一致？③ 用户能区分"具体的回应"和"空话"吗？

洞察 3：共享底线

原文结论：不同人格可以有不同性格，但有一层共享的 BASE_TRAITS——不说教、不评判、不催促。人格可以不同，底线必须一致。

延伸结论：共享底线是"产品价值观的工程化落地"。共享设计比"按角色各自定义底线"更安全、更易维护、更具扩展性。底线是"人格的护栏"——人格在护栏内自由发挥，越界即触发降级。

机制拆解：System Prompt 四层结构——人格层、底线层、气质层、上下文层。易变的部分（人格）按场景切换，不变的部分（底线）跨场景复用。这是"关注点分离"的 prompt 工程思路。

需要验证：① 共享底线是否确实让所有角色"不越界"？② "绝对禁止"措辞是否会让模型过度收敛？③ 底线规则在不同服务商模型上的遵守度？

洞察 4：长在用户身上

原文结论：让 AI 的人格"长在用户身上"，而不是一个固定的模板。但自定义气质存在实际生效度问题。

延伸结论：用户自定义是"显式信号"，画像是"隐式信号"。两者结合才能让 AI 既"像用户要的"又"理解用户真实状态"。但画像存在"时差"问题——基于过去数据，不一定反映当前状态。

机制拆解：自定义气质生效度低的原因是大模型注意力机制的"远端衰减"——System Prompt 后部内容对输出的影响弱于前部。这是 transformer 架构的固有特性。

需要验证：① customPersona 移前部能否显著提升生效度？② 6 家服务商对自定义气质的遵循度差异？③ 画像注入的"有效样本量阈值"？

洞察 5：安全边界

原文结论：人格的生动是有边界的。危机时刻人格必须切换，人格是体验层，安全是底线层。

延伸结论：危机模式是"人格的紧急熔断"——人格不能阻挡安全底线。危机识别采用"双重保险"机制：前端关键词预筛 + AI prompt 语义识别，宁可误报不可漏报。危机响应时需要"覆盖式切换"——人格在危机时刻不应该还残留。

机制拆解：正常模式优先级：人格描述 > 共享底线 > 用户气质。危机模式优先级：危机协议（最高优先级，覆盖所有层级）。

需要验证：① 双重机制实际拦截率？② 前端关键词误报率？③ 危机模式中人格是否"完全消失"还是会"渗透"？

洞察 6：情绪陪伴不适用自主 Agent

原文结论：情绪陪伴的核心是"用户被看见、被接住"，不是"AI 替用户解决问题"。AI 的克制比 AI 的聪明更重要。

延伸结论：引入 Agent 自主链路等于把"用户定义自己感受"的权利让渡给 AI，是对用户主体性的根本性侵犯。情绪场景的容错率远低于任务场景。可以探索"被动增强"中间地带——AI 记住偏好，用户主动调用时推荐。

机制拆解：Agent 化（自主分析 → 自主决策 → 自主执行）与情绪陪伴（被看见 → 被接住 → 自己做决定）在"决策权归属"上结构性冲突。Agent 越自主，用户主体性越被削弱。

需要验证：① 用户是否真的希望情绪陪伴"不替我做决定"？② "被动增强"模式的实际效果？③ 用户对"AI 主动给情绪建议"的接受度？

洞察 7：任务拆解 / 完成鼓励适用 Agent

原文结论：任务拆解的本质是"帮用户甩掉反复斟酌的决策包袱"。完成鼓励可以结合画像动态调整反馈表达。

延伸结论：Agent 化的边界是"可计算的客观决策"——跨越这个边界就进入情绪场景。Agent 的真正价值不是"更准的安排"，而是"替用户承担决策疲劳"。完成鼓励 Agent 化需要注意"鼓励通胀"风险——失去具体性的鼓励反而损害信任。

机制拆解：任务场景的决策可计算（外部可验证）→ AI 可以代理决策 → Agent 化合理。用户希望减负（决策疲劳）→ AI 自主 = 用户少消耗 → Agent 化有价值。行为数据可沉淀（数据化）→ Agent 化有数据基础 → Agent 化可落地。

需要验证：① Agent 化任务拆解是否确实"替用户承担决策疲劳"？② 用户控制感是否被削弱？③ 鼓励通胀问题是否出现？④ 数据沉淀的"够用阈值"？

洞察 8：陪伴 vs 解决 / 记得 vs 越界

原文结论：判断模块是否适合 Agent 化，用两个维度：陪伴 vs 解决（核心价值判断），记得 vs 越界（隐私感边界）。

延伸结论：陪伴 vs 解决是一个连续谱，不是二元分类。晚安疗愈和日记回应是"用陪伴的方式提供解决"——既要让用户安心，也要提供洞察或力量。日记的"记得"边界最敏感，需要"选择性记得"——记住用户愿意被看见的部分，对脆弱的部分保持"不知道"。

机制拆解：两个维度都是从"用户感受"出发判断，不是从"AI 能力"出发。这呼应了产品价值观："用户是主体"——Agent 化的判断标准不是"AI 能不能做"，是"用户会不会因此更舒服"。

需要验证：① 晚安疗愈的"个性化温度"是否确实让用户感受更好？② 用户对"AI 记住情绪色调"的接受度？③ 日记回应的"选择性记得"边界在哪？④ 用户对"功能克制"是否真的更满意，还是会觉得"产品不够智能"？

八个洞察的层次结构

把八个洞察放在一起看，可以发现一个清晰的层次结构：

【价值观层】（最根本）
  洞察 5 安全边界 — 危机时刻人格必须熔断
  洞察 6 情绪陪伴不自主 — AI 是陪伴者不是决策者

【机制层】（如何实现价值观）
  洞察 1 人格与场景匹配 — 基础机制
  洞察 2 反空话套话 — 具体性约束
  洞察 3 共享底线 — 价值观的工程化
  洞察 4 长在用户身上 — 个性化的两条路径

【应用层】（如何落地到具体场景）
  洞察 7 任务拆解/鼓励 Agent 化 — 解决型场景的智能化
  洞察 8 陪伴 vs 解决 / 记得 vs 越界 — 开放型场景的判断框架

这个层次结构说明：AI 人格设计和 Agent 边界判断不是孤立的产品决策，是"价值观 → 机制 → 应用"的完整链路。没有价值观层的清晰，机制层就只是工程技巧；没有机制层的支撑，应用层就只是空中楼阁。

第四层：反思与展望

这算什么产品能力

写到这里，我在想：这个"人格设计 + Agent 边界判断"的能力，到底算产品开发的哪个维度？

我觉得它至少横跨了两个维度。一个是"AI 品位"——知道什么时候该让 AI 更像人（人格设计），知道什么时候该让 AI 保持克制（不自主），本质上都是对"AI 能力边界"的感知。AI 不是越像人越好，也不是越智能越好，是在对的场景用对的方式。

另一个是"产品价值观"的延伸。情绪陪伴不引入 Agent、晚安疗愈要小心保持陪伴底色，这些决定背后都是同一个价值观：用户是主体，AI 是陪伴者。AI 可以帮用户减负（任务拆解），但不能替用户做决定（情绪陪伴）。

人格设计解决的是"AI 像不像人"，Agent 边界解决的是"AI 该不该替人做决定"。这两个问题放在一起看，其实是一体两面：一个 AI 越像人，越要清楚它什么时候可以自主、什么时候必须克制。

和前几个 Case 的关联

这个思考不是孤立的，它和之前几个 case 指向同一个方向。

前几个 case 论证了"产品需要一个 AGENT 编排层"，这个思考则补充了"编排层应该怎么设计"——不是所有模块都适合 Agent 化，情绪陪伴要守住不自主的底线，任务拆解和完成鼓励可以放心交给 Agent。编排层的第一个能力是调度决策，但调度决策的自主权边界，需要和人格设计一起考虑。

总结与展望

至此，我从四个层面拆解了 AI 人格设计与 Agent 适用边界这个问题：第一层是人格机制——反空话套话、共享底线、长在用户身上、安全边界，四个让 AI "像人"又不"过度像人"的设计方法；第二层是 Agent 边界——情绪陪伴不自主、任务拆解/鼓励可自主、晚安/日记待定，一个"用户感受优先"的判断框架；第三层是纵深推演——八个洞察的延伸结论、机制拆解、验证要点，是从"知道"到"能用"的落地桥梁；第四层是反思定位——AI 品位与产品价值观的交汇，AI 时代产品人的新能力维度。

展望下一步，方向有三个。验证优先：从第三层的"需要验证"清单里挑 2-3 项做测试，建议优先验证"反空话套话"的效果度量和"情绪陪伴不自主"的用户接受度。被动增强先行：在情绪陪伴模块探索"被动增强"模式（AI 记住偏好，用户主动调用时推荐），这是"不自主"和"更智能"之间的务实路径。AGENT 编排层规划：把这些思考和前几个 case 的结论（时间安排、过期处理、API 兼容性）统一纳入 AGENT 编排层的设计原则。

这篇回答了什么产品问题：产品「不做什么」和「做什么」为什么同样重要？——「不评价」的产品价值观如何落到具体的功能取舍上。

不做什么：我主动放弃了打卡模块

做 StepForward 时，我做了个反主流的决定：不做打卡。连续 7 天给勋章、断签弹红字，是同类产品的常规操作。想了几天，我决定永远不做——不是还没轮到，是写进了"不做清单"。

原因不在方法论里，在我自己身上。我的目标用户就是我这样的人：行动力瘫痪，被"做不到"的感觉压住；完美主义，做不完美宁愿不做。这两条不是调研出来的，是用自己被它们折磨的体验反推的。

拿这两条去推演打卡。连续打卡是冲着"每天坚持"的考核，状态起伏大的人做不到。连打 5 天，第 6 天状态差没完成，弹一句"你已断签 1 天"——对一个本来就自我怀疑的人，这就是"你果然不行"。更糟的是，有人会为了不断签干脆不打开产品，一去不复返。就算没断，勋章的开心也只能撑几分钟。

后来想明白了，打卡的本质是产品在对用户做评价，把一天分成"成功"和"失败"。可我的用户每天对自己的评价已经够多了。

所以我给产品定了底色：不评价。没有连续天数，没有勋章墙，没有排行榜。完成一个步骤，AI 给你一句温暖的话，这是反馈；没完成，AI 陪你聊聊为什么，这是陪伴。反馈可以有，评价不能有。我连"今日任务"的叫法都改成了"待办步骤"——只说"还有这些可以选"，不暗示"必须做完"。这个原则一直延续——ROADMAP 里"偶然发现式成就"的思路储备，我特意标注不做徽章墙、不做打卡、不设目标。

有人会问：打卡明明提升留存，你不要，是产品能力差吗？不是。打卡确实涨 DAU，但涨的每一分都建立在用户自我感受更糟的前提上。行业清一色做打卡，是默认用户缺的只是推力；我的用户缺的是安全感。"我是不是错了"的念头反复出现过，我的办法是回到原点：我的用户是谁？打卡对她的痛点是缓解还是加剧？答案始终是加剧。

"做什么"有反馈，指标涨了看得见；"不做什么"零反馈，没人告诉你损失了什么，只能自己想清楚。这就是产品价值观——用户值得被尊重而不是被考核，产品该让她活得更好，而不只是用得更多。

写这篇时我问过自己：是不是想多了？后来觉得不是。大到成就系统，小到一个红字，都在悄悄传递"我对你有要求"。我的产品想传递相反的东西：我没有要求。你来，我陪你；你走，我等你。

这篇回答了什么产品问题：一个时间安排 bad case 如何引发对架构的反思？——从修 bug 到追问系统性根因的完整排查过程。

时间安排 Bad Case 排查：当规则被严格遵守，结果却违反常识

测试产品时，我随手输入"中午吃午饭"，AI 把"吃午饭"排到了 11:00。产品明明有午餐时间设置（12:00-13:30），它为了避开，把午饭挪到了 11 点。

又试了"现在写报告 2 小时"，当时 23:00，AI 把它排到第二天 9:00——我明确说了"现在"，但 23:00 不在工作时间内，规则把它推到了明天。

功能没坏，规则被严格遵守了，结果违反常识。这就是 bad case——bug 用户会报错，bad case 是结果很蠢，用户只会默默离开。

定位到 buildTaskPlannerPrompt，两条硬约束："严格在工作时段内安排""不要排在用餐时段内"。根因是我把设置当成了枷锁：用户设"9:00-18:00"本是"我通常在这段时间做事"，写进 prompt 却变成"只能在这段时间安排"。这偏差 v2.0.4 上线时暴露不出来——测试用例都是"写周报"这类标准场景，直到用户输入生活化的东西。

方案探索走过弯路。我担心 AI 判断模糊时间不可靠，想过前端预过滤弹窗，推演后否了："晚上做 PPT"的"晚上"是几点，本质是 NLP 问题，前端硬代码做等于重新实现一个 mini AI；而且目标用户被事情压着，让他在输入框里纠结"几点几分"是反人性的。

最终 v2.2.3 落地的是 prompt 改造加前端兜底：用户意图优先提到最高级，工作/用餐时间降级为默认偏好，吃饭类任务主动放进用餐时段；返回结果用关键词白名单二次校验，说"现在"而偏差超 2 小时的修正回来。

有个我很看重的判断：区分有害的 bad case 和无害的不一致。吃午饭排到 11 点、说了"现在"被推到明天，是信任破坏，必须修；"下午"理解成 14:00 还是 15:00，差一小时感知不到。只修质变，不修量变。

方案没彻底解决问题——ROADMAP 里挂着一条已知未解决场景：用餐时段内输入"写作业"，AI 没避开。长期跟踪中。

排查还让我看到下一步：现在的 AI 只是执行引擎，画像、情绪记录、日记数据都在，但没串起来。编排层若能注入"用户最近三天午餐在 12:00-12:30"，AI 就不用靠规则猜"中午"是几点。调度决策收归 AGENT 编排层，记进了规划。

过期任务处理：一个功能做到一半，我却决定停掉

用户几天没打开 StepForward，过期的任务怎么办？这是 v2.2.5 遇到的问题。第一轮先修用户反馈的"后推"bug——过期任务全堆到当前时间 +30 分钟，改成"顺延到明天"：按原时间 +24 小时。第二轮加冲突检测：可能撞上已有安排，撞了就弹窗三选一。

做到这里，顺延按钮点了没反应。debug 时脑子里冒出一个更大的问题：这事是不是从根上就不该用硬代码做？

越想越不对。顺延一天太粗糙——明天那个时间真有事呢？连三天没打开，任务一路顺延到下周，还有意义吗？冲突检测也粗糙，只能判断时间重叠，可用户明明可以直接问 AI"这些过期的怎么安排"。更要命的是，每多一个边缘情况就多一段代码：过期处理、冲突检测、跨事件偏移、用餐规避……prompt 管 80% 的正常情况，硬代码补 20% 的边缘，补丁自己还会出 bug——按钮没反应就是一个。

数了数代码里和调度相关的逻辑：拆解 prompt、findTimeConflicts 冲突检测、冲突弹窗、shiftAllSubsequentTasks 整体偏移、过期批量处理、关键词兜底，散在至少 5 个函数里。每一处都在做调度决策的一部分，却没有统一的决策者。突然反应过来：拆解、排期、冲突、重排，本质都是调度——这是 AI 擅长的事，我却在用硬代码拼。

我把"顺延到明天"下架了，只保留删除、先不动、已完成三个动作。理由很实际：纯前端加 localStorage，没有编排层的基础设施，硬做只会把简单的事搞复杂；用户的核心痛点也不是"过期任务能不能智能重排"，是"敢不敢开始第一步"。等 Phase 2 后端升级、AGENT 编排层建起来，调度决策收归 AGENT——到那天不是"再加一个功能"，是调度能力自动具备。

这个 case 和时间安排 bad case、多服务商 API 兼容性指向同一个方向：prompt 加兜底总有覆盖不到的场景；服务商挂了用户不该感知；重排靠硬代码越做越复杂。答案都是 AGENT 编排层。现在的硬代码兜底，都是"没有 AGENT 的时代做 AI 产品"的权宜之计。分清什么是当下不得不做的妥协、什么是未来的正确方向——这是这次"做着做着停下来"里最值钱的判断。

多服务商 API 的 Maintenance Case：你什么都没做，但东西坏了

那天产品好好的，我一行代码没改，用户反馈 AI 调不了了。查了半天，是 DeepSeek 更新了模型，代码里写死的旧模型名直接 404。不知道坏了多久，可能已经三天了，直到用户反馈才发现。

我给它归了类：bug 是代码写错，bad case 是功能能用但结果蠢，maintenance case 是外部依赖变了、你没跟上，所以坏了。最难受的是第三种——什么都没做错，东西却坏了，而且静默。

StepForward 接了 6 家服务商：DeepSeek、Minimax、OpenAI、智谱、通义千问、Anthropic，配置全硬编码在 api.js 里，每家要维护 API 地址、模型 ID 列表、请求体构建、响应解析等五六项。resolveModel() 做模型名回退，但只能防"用户缓存了旧模型名"，防不了"代码里写死的名字过期"。6 家就是 6 个要盯的变化源，不可能每天看 6 家 changelog。

调研了成熟产品：LangChain 的适配器、Dify 的插件工厂、LiteLLM 的统一代理、OpenRouter 的聚合，核心都是把差异收敛到一处。但没急着改代码——纯前端阶段，很多方案依赖后端。现在是人工巡检 6 家 changelog 加 resolveModel() 回退；后端升级后走集中配置、前端健康检查、统一代理。

回头想为什么做成"每家手写一份"：接第一家写一份，第二家复制粘贴改一改，增量成本看着很低——直到服务商更新，你发现 6 份代码都要改，还不知道哪份会出问题。好的架构不是"写的时候爽"，是"改的时候不痛苦"。这道理软件工程讲了几十年，但只有亲自经历过一次，才理解那些"多余"的架构设计是干什么的。

排查让我定了三条标准。外部依赖越多，维护成本越被低估——接多少家不只是功能决策，也是维护能力决策。可靠性是最基础的产品力——产品再温暖，经常"用不了"用户就会离开，而且静默，用户只会默默不用。Agent 编排层应该包含自动恢复——一家失败就自动降级切下一家，用户不需要知道 API 更新过，只需要知道产品一直能用。

demo 只需要能用，产品需要一直能用。维护不是运维的事，是产品的事。

缓存命中率下降排查：一次隐性成本的 troubleshooting

做 StepForward 时我一直盯着 token 消耗——靠大模型驱动的产品，每次调用都在浪费的话，用户量一上来成本会很难看。

有天我对比了 v2.0.0 和 v2.2.3 的缓存命中率。新版本功能多，调用量涨正常，但命中率不该掉这么多——DeepSeek 的 prompt cache 按前缀匹配，system prompt 不变就该稳住。数据说不是。

把两个版本的代码拉出来对着看。v2.0.0 简单：3 个角色，system prompt 基本固定，命中自然好。v2.2.3 复杂得多，9 个 API 调用点。顺着 buildSystemPrompt 读下去，问题出现了——system prompt 末尾动态注入用户画像，画像来自埋点，每完成一个任务、每表达一次情绪都会更新。system prompt 在持续变化，前缀哪怕变一个字，算好的 KV cache 也会全部作废。

继续挖掘，还有别的缓存杀手：拆解 prompt 开头写着"当前时间：9 月 1 日 14:30"，每天变，缓存每天重建；角色从 3 个涨到 5 个，前缀不同，各占一个缓存位；max_tokens 从 1024 涨到 4096，字段不进 prompt，但参与缓存 key 计算。

从根源上看，代码本身没有坏，产品跑得好好的，用户感知不到异常——它是功能叠加时只看功能生效、不看底层代价的典型陷阱。画像功能本身成立，问题只在注入位置：同样的信息放 system prompt 还是 user message 末尾，体验几乎没差，成本差一个量级。

整理出 6 个优化方向，按收益排序。收益最大的两个：画像移出 system prompt、日期时间移出 prompt 前缀；其次统一各角色 system 前缀、情绪分类改用关键词匹配——分类这种任务用正则就够，何必烧 token。也想过上 RAG 做画像检索，很快否了：RAG 本身就是动态注入，先引入一个让缓存更差的东西再指望它省钱，逻辑是反的。

这些方案目前停在"已设计、暂不实施"——现阶段用户量小，体验优先。但排查让我确定了两个标准：成本意识是产品 sense 的一部分，命中率 80% 和 20%，规模化后就是 4 倍成本差；AI 品位体现在用户看不见的地方。

我的 AI 模型切换场景笔记

开发 StepForward 期间攒的一些模型选择直觉——不是系统评测，是用出来的体感。

规则很简单：小改动求快，大改动求稳。改按钮文案、调 prompt 措辞，用 Flash；重构整个模块、排查安卓卡死、气泡定位这类复杂 bug，上 Pro——要读大量代码、分析根因，Flash 容易漏。新功能第一版用 Pro 搭骨架，小修小改换回 Flash。

翻过一次车：改跨日排期时图快用 Flash，漏改了三个函数，调了半天才发现。打那以后，多文件联动的改动我直接上 Pro。

什么时候换模型？说白了就是 DeepSeek 搞不定的时候。同一个 bug 排查两轮没结果，换——同一个模型容易陷在同一个思路里。prompt 试了好几版都不行，也换——换模型有时比改 prompt 见效快。方案拿不准就两个模型各问一遍，都说行就稳很多。各家风格确实不同：DeepSeek 偏工程化适合写代码，GLM 更细致，Kimi 长上下文稳。

任务拆解场景 Flash 够用：简单任务两者差不多，Flash 还快；复杂任务 Pro 拆得细一点，但用户在确认循环里自己调整就好。所以演示模式固定用 DeepSeek Flash：拆解本质是结构化输出，不需要深度推理；速度快、成本低，HR 打开 demo 放开用。

情绪陪伴是另一回事：写代码看逻辑，陪伴看语气暖不暖、会不会说空话、能不能接住情绪而不是急着给方法。Flash 偏理性，回应"正确"但温度稍弱。我的处理不是依赖模型的输出倾向，而是用 System Prompt 立规矩——反空话套话，7 条禁止加 5 条必须，把回应框在温暖、不评判、不说教里。模型是基础，prompt 设计直接决定体验质量。

被模型生态打过几次脸。模型名说下线就下线，旧端点一关产品直接报错；DeepSeek 升级 API，流式输出格式变了一点，前端解析出错，表现是"AI 回复一半就停了"，查了三轮才发现根因不在前端；模型升级后同一个 prompt 效果也可能变——代码没改，体验变了。所以核心 prompt 要有效果基线，升级模型后要重新验证。

对 AI 产品来说，"前沿敏感"不是知道多少模型名字，是知道哪个模型适合干什么、知道它会变会坏——选对场景，也为选错留好后路。
